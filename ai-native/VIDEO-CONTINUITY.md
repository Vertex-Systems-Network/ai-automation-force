# Video Continuity Architecture

## Goal

Build long-form children's videos from short AI-generated clips while preserving characters, scene state, visual style, camera logic, timing, and story continuity across providers.

## Important limitation

Cross-provider continuation can be made robust, but it cannot be guaranteed to be pixel-perfect or motion-perfect. Different video models use different internal representations. Therefore the system must not depend on an undocumented assumption that Provider B can literally continue Provider A's latent generation state.

The reliable strategy is to preserve an external canonical continuity state that every provider can consume.

## Do not build a 2-minute video as one endless chain

For a 1–2+ minute video, avoid:

`clip 1 -> extend -> extend -> extend -> extend -> ...`

because small identity, wardrobe, lighting, camera and geometry errors accumulate.

Preferred architecture:

`master audio -> timed storyboard -> canonical keyframes -> short shots -> continuity QA -> deterministic assembly`

Each shot is usually 4–8 seconds, or another provider-supported duration.

## Canonical shot package

Every shot has a provider-independent package:

- `shot_id`
- global video ID
- timeline start/end
- exact audio segment/timecode
- narration/lyric line
- story beat
- characters present
- character reference IDs
- expression/state
- wardrobe state
- prop state
- environment state
- lighting/time-of-day state
- camera framing
- camera movement
- motion intent
- visual style ID
- first-frame image
- target/end-frame image when available
- continuity anchor frame
- reference image pack
- provider prompt
- negative constraints
- previous shot ID
- next shot ID
- provider/model actually used
- generation ID
- seed when exposed by provider
- output hash
- QA score
- retry count

## Canonical first/last keyframe strategy

Before expensive video generation, create or approve keyframes for the whole sequence.

For shot N:
- `first_frame_N` is derived from the prior approved visual state;
- `last_frame_N` is the planned state that should hand off into the next shot;
- `first_frame_N+1` should match or intentionally transition from `last_frame_N`.

This makes provider switching much safer than asking a new model to infer continuity from text alone.

## Native continuation path

If the current provider officially supports extending its own generated video, prefer native extension when:
- the previous clip is clean;
- identity is stable;
- the next beat is a true continuation of the same shot;
- free/paid policy allows it.

Example: current Veo 3.1 documentation supports extending videos previously generated by Veo.

Still store external continuity anchors before extension so the project can recover if that provider becomes unavailable.

## Cross-provider continuation path

When switching from Provider A to Provider B:

1. freeze Provider A's final approved frame;
2. extract a clean continuity anchor from the last stable frame(s);
3. load canonical character/style references;
4. load exact scene-state JSON;
5. use the final frame as Provider B's first-frame/image-to-video reference when supported;
6. provide the planned target/end frame when Provider B supports keyframes/end frames;
7. repeat the unchanged identity/style constraints;
8. generate only the next shot, not the remaining full video;
9. run continuity QA before accepting;
10. retry or choose another provider if the continuity threshold fails.

This produces a visual handoff, not a shared hidden model state.

## Overlap strategy

For difficult transitions, generate a small logical overlap between shots:
- preserve the final pose/action from the previous shot;
- begin the next shot from the same visual anchor;
- cut at the best matching frame during deterministic editing.

Do not necessarily expose duplicate seconds in the final edit.

## Continuity QA

Every proposed clip must be compared against the canonical shot state and adjacent approved clips.

Check:
- character identity;
- face/body proportions;
- clothing/colors/accessories;
- prop existence/location;
- environment geometry;
- palette/lighting;
- image style;
- camera direction;
- motion direction;
- temporal logic;
- lip/speech timing when applicable;
- no unexpected text/logos;
- no new/vanishing limbs/objects;
- no sudden age/species/style changes;
- end-frame suitability for the next shot.

Use a multimodal AI judge plus deterministic checks where useful. Reject the clip when critical continuity fails even if it looks visually attractive.

## Continuity score

Store component scores, for example:

- identity: 0–100
- wardrobe: 0–100
- environment: 0–100
- style: 0–100
- camera: 0–100
- action: 0–100
- temporal transition: 0–100
- safety: pass/fail

Critical failures cannot be averaged away.

## Provider capability routing

The router should prefer, in order for a continuation-sensitive shot:

1. provider-native extension of the same approved clip;
2. first-frame + last-frame/keyframe generation;
3. image-to-video from canonical first frame with reference images;
4. reference-video/video-to-video generation;
5. text-only generation only when the shot does not require strict continuity.

A provider with free credits but weak continuity support should not automatically beat a better free provider that supports the required anchors.

## Veo 3.1 example

Current Veo 3.1 documentation states:
- 8-second video output;
- video extension for videos previously generated using Veo;
- first/last-frame generation;
- up to three reference images.

Therefore a 2-minute production should use Veo as a shot engine, not assume a single 2-minute call.

## Long-form example

For a 96-second song:

- master audio: 96s
- storyboard: 14–20 shots depending on pacing
- each shot: approximately 4–8s
- some chorus shots may reuse established locations/visual motifs without reusing identical video
- keyframes locked before video generation
- clips generated through the free-tier/cost router
- failed continuity clips regenerated
- final assembly follows exact audio timecodes

## Generation history

Maintain a permanent generation ledger for every attempt, including rejected attempts:

- run ID
- content ID
- video ID
- shot ID
- attempt number
- provider/model
- access tier
- prompt version/hash
- source assets and hashes
- first/end frame hashes
- generation ID
- requested duration
- actual duration
- output hash/location
- continuity scores
- rejection reason
- credit/cost estimate
- license/watermark status
- timestamp

Do not delete rejected attempt metadata; it teaches the agent what failed and prevents repeating the same prompt/provider combination blindly.

## Binary asset policy

Do not bloat the Git repository with every raw video binary by default.

Git stores:
- manifests;
- prompts;
- hashes;
- metadata;
- QA;
- canonical keyframe references;
- provider run IDs;
- asset locations.

Large media can live in a configured asset store/local workspace/Git LFS only when intentionally enabled. The repo remains the source of truth for state and provenance.

## Recovery after free quota exhaustion

If a provider stops at shot 7 because free capacity is exhausted:

- mark shot 7 complete;
- persist its final continuity anchor;
- persist all generation metadata;
- choose the next eligible provider;
- hand the new provider the same canonical state;
- continue from shot 8;
- never regenerate shots 1–7 merely because the provider changed.

## Quality principle

`free` is a routing preference, not permission to accept malfunctioning output.

A free generation that breaks character continuity should be rejected. The system may wait for another free quota/provider rather than silently lower the quality threshold.
